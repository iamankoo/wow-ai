# The WOW dataset: pipeline and long-term strategy

This document covers `training/pipeline/` - the production-grade dataset
infrastructure for WOW's long-term call/voice-command dataset (the "v3+"
track), separate from and additional to the v0/v1/v1.1 pipeline documented
in `docs/TRAINING.md`. Read this if you're adding data, running the
pipeline CLI, or deciding what the next dataset version should contain.
Read `docs/TRAINING.md` if you're training a classifier.

## Dataset philosophy

**The honest framing is "1M+ examples is the long-term target," not "here
is 1M examples."** Nobody can hand-author a million genuinely diverse
examples in one sitting, and mechanically generating that many via
templates would fail the one requirement that actually matters: real
semantic diversity, not superficial variation counted as if it were
diversity. So this pipeline is built to make reaching that target
*possible* over time - through real infrastructure (dedup, quality
scoring, versioning) and multiple legitimate sources - rather than
pretending a single batch gets there.

The growth path, in order:

```
high-quality hand-authored seed  (this document, v3.0.0-seed)
    -> legitimately licensed external data (researched, not yet ingested - see below)
    -> reviewed production feedback (docs/SELF_LEARNING.md's feedback pipeline)
    -> active learning (low-confidence predictions reviewed by real users)
    -> hard-negative mining (docs/SELF_LEARNING.md's FailureMiner)
    -> additional curated rounds
    -> future dataset versions (v3.1, v3.2, ... v4.0)
```

Every stage after the first produces real, provenance-tracked data - none
of it is ever backfilled with synthetic padding just to hit a number.

## What exists today: v3.0.0-seed

333 hand-authored examples (`training/datasets/v3_raw/seed.jsonl`,
generated by `training/pipeline/generation/build_v3_seed.py`), scored and
split into `training/datasets/versions/v3.0.0-seed/`. This is explicitly
an **initial seed batch for the v3+ pipeline**, not a production-ready
standalone training set (329 passing examples across 17 intents averages
~19 examples/intent - well below the 30+/intent floor v1.1 established;
see "Remaining gaps" below). Its purpose is to validate the pipeline
end-to-end with real, high-quality data and establish the Hindi-dominant
language direction, not to replace v1.1's already-larger, English-leaning
dataset (`training/datasets/versions/v2.1.0/`) - the two tracks are
independent; see `docs/TRAINING.md` for the v0/v1/v1.1 track.

## Taxonomy

Intent/context/action labels are the existing WOW taxonomy
(`backend/app/brain/taxonomy.py`, re-exported via
`training/wow_taxonomy.py`) - this pipeline never defines a parallel label
set. `training/pipeline/label_validate.py` enforces this: every example is
checked against `is_valid_intent`/`is_valid_context`/`is_valid_action`.

### Mapping the full call-assistant domain onto the existing taxonomy

Many real-world call-handling situations map onto existing taxonomy
members rather than needing new ones:

| Situation | Taxonomy mapping |
|---|---|
| Driving, studying, eating, exercising, in class, at work, on another call, with family/friends, at a religious/social event | `ContextMode.CUSTOM` (the situational detail lives in the example text, same pattern as the existing "at a family function" example) |
| Caller asking for the user / who WOW is / whether the user is available | `GENERAL_CONVERSATION` or `KNOWN_CALLER`/`UNKNOWN_CALLER` depending on whether the caller is identified |
| Missed call / call history / callback request | `SCHEDULE_REQUEST` (a callback is a scheduling request) or `MESSAGE_FOR_USER` |
| Escalate urgent call | `URGENT_CALL` / `Action.MARK_URGENT` |

### Proposed taxonomy expansion (not implemented - for your decision)

A few call-management concepts genuinely have **no clean mapping** onto the
current `Action` enum and were *not* silently forced into an existing one:

- **Hold call / resume call** - no `HOLD_CALL`/`RESUME_CALL` action exists.
- **Reject call** (explicitly declining, distinct from `END_CALL` on an
  already-connected call or `DISABLE_CALL_ASSISTANT`) - no dedicated action.
- **Redial** - no dedicated action; closest is `CALL_PERSON` (intent) with
  no action distinguishing "redial the last number" from "call a named
  person."

These are flagged here rather than added, per the standing rule that
taxonomy changes need your explicit sign-off before implementation
(taxonomy is production-facing - `backend/app/brain/taxonomy.py` - and a
change there affects the live provider contract, not just training data).
If you want these covered, the smallest correct change is three new
`Action` enum members (`HOLD_CALL`, `RESUME_CALL`, `REJECT_CALL`) plus
matching `ACTION_DESCRIPTIONS` entries; `REDIAL` likely doesn't need a new
action if it's modeled as `CALL_PERSON` with a `parameters={"redial": true}`
hint instead.

## Language distribution

Target: Hindi ~60% / Hinglish ~30% / English ~10% (the inverse of the
v1/v1.1 track, reflecting WOW's actual target user base). **Achieved in
v3.0.0-seed: Hindi 60.1% (200), Hinglish 24.3% (81), English 15.6% (52)** -
close to target on Hindi, somewhat short on Hinglish and over on English.
Reported honestly rather than adjusted to look exact; the shortfall is a
natural target for the next round of additions.

Hindi is primarily Devanagari script by design (not Roman-transliterated
Hindi, which was the v1/v1.1 convention) - this is the biggest linguistic
difference from the earlier track.

### Language classification

`training/pipeline/langid.py` provides a **heuristic, not ground-truth**
language classifier - Devanagari-script ratio for Hindi, a curated
Romanized-Hindi function-word list (with common English loanwords like
"call"/"message"/"meeting" excluded from the count, since using them
doesn't make a sentence less Hindi) for distinguishing Hindi/Hinglish/
English in Latin script. It's used to *flag* declared-vs-detected
mismatches for review, never to silently overwrite an author's label.

Building v3.0.0-seed surfaced a real, instructive case: sentences using
only English *loanwords* in otherwise all-Hindi grammar ("Boss ko call
kardo abhi ke abhi") were initially hand-labeled "hinglish" by convention,
but the heuristic flagged them as "hi" - and on reflection, that's the
more linguistically defensible call (loanword borrowing isn't the same as
grammatical code-switching). Those 25 examples were relabeled to "hi" at
the source, and ~30 new examples with genuine grammatical mixing ("I think
usko bata dena chahiye ki main busy hoon") were added to keep Hinglish
represented by real code-switching rather than loanword-only Hindi. Final
concordance on v3.0.0-seed: 329/333 (98.8%) - the remaining 4 are
genuine boundary cases, left flagged for review rather than forced either
way.

## Quality standards

Every example passes through `training/pipeline/quality.py`'s composite
scoring before being eligible for a split:

1. **Label validation** - real taxonomy members only.
2. **Hard-negative validation** - if `hard_negative=true`, a recognized
   `confusable_pair` and explanatory `notes` are required.
3. **Language consistency** - heuristic check (see above), soft signal.
4. **PII detection** - see below.
5. **Length bounds** - 2-500 characters.
6. **Exact/near-duplicate detection** - see below.

Each dimension either fails hard (`reject`: invalid labels, exact
duplicates, out-of-bounds length - these never enter a split) or soft
(`review`: language mismatch, PII redacted, near-duplicate - excluded from
the default split but not deleted, awaiting a human decision). A clean
example scores 1.0 and status `pass`. Nothing is silently dropped -
`training.pipeline.cli stats` reports the full status distribution and
every rejected/reviewed example's specific reasons are computed by
`quality.score_example` and inspectable via `cli inspect`.

## PII policy

**No real user data is in this pipeline at all** - v3.0.0-seed is 100%
hand-authored, and 0/333 examples triggered PII detection (expected, since
no author put real phone numbers/emails in synthetic examples). The
policy for any *future* source that might carry real PII (a legitimately
licensed dataset with real transcripts, or production feedback per
`docs/SELF_LEARNING.md`) is: `training/pipeline/pii.py` reuses
`backend/app/learning/privacy_filter.py`'s `RegexPrivacyFilter` - the
exact same regex-based phone/email/card/OTP redaction used for the
production feedback pipeline, so there is one PII policy across the whole
project, not two. See `docs/SELF_LEARNING.md` "Privacy filter limitations"
for what it does and doesn't catch (regex-based, not NER - a bare name in
prose isn't caught).

## Deduplication

- **Exact**: content-hash based (`training/pipeline/dedup.py`), via
  `RawExample.example_id()` - normalized (case/whitespace/trailing
  punctuation insensitive) text + language. O(n), scales to millions.
- **Near-duplicate**: character 4-gram Jaccard similarity (default
  threshold 0.85), bucketed by (language, first shingle) so comparison
  stays local rather than all-pairs. This catches near-identical phrasing
  ("I'm busy right now, take messages instead." vs "...please take
  messages instead.") but **not paraphrases in different words** - that
  needs embeddings, which this pipeline deliberately doesn't depend on at
  this dataset size (see "Scaling strategy").

v3.0.0-seed: 0 exact duplicates, 0 near-duplicates (verified via
`cli dedupe`, not assumed).

## Semantic diversity (anti-templating)

`training/pipeline/diversity.py` computes, per intent: average pairwise
character-shingle similarity and type-token ratio (vocabulary richness)
across that label's examples. A label that's the same sentence with one
word swapped repeatedly scores high similarity + low TTR ("high"
templating risk); genuinely varied phrasing scores low similarity + high
TTR. **Every one of v3.0.0-seed's 17 intents scored "low" templating
risk** (avg similarity ≤0.061, TTR ≥0.52 for every label) - measured, not
asserted; see `training/datasets/v3_raw/seed.stats.json`
`diversity_by_intent` for the full per-label numbers.

## Hard negatives

`training/pipeline/label_validate.py:CONFUSABLE_PAIRS` is the source of
truth for which confusable-pair categories are tracked:

```
URGENT_CALL vs NON_URGENT_CALL
KNOWN_CALLER vs UNKNOWN_CALLER
SET_CONTEXT vs GENERAL_CONVERSATION
GET_CONTEXT vs SET_CONTEXT
END_CALL vs END_CONVERSATION
MESSAGE_FOR_USER vs GENERAL_CONVERSATION
CALL_PERSON vs HANDLE_CALLS
CLEAR_CONTEXT vs DISABLE_CALL_ASSISTANT
```

Every `hard_negative=true` example must declare which pair it targets and
explain the trap in `notes` - enforced by `validate_hard_negative`, not
just a convention. v3.0.0-seed has **25 hard negatives, 3-4 per pair**
(all 8 pairs covered) - see `training/pipeline/generation/build_v3_seed.py:build_hard_negatives`.

## Versioning

`training/pipeline/versioning.py` writes each dataset version to
`training/datasets/versions/<version>/` with a `MANIFEST.json` recording
every file's SHA-256 checksum, size, and line count - `cli version verify
<version>` recomputes and compares, so "did this training run actually use
the data I think it did" is always independently answerable, not just
trusted by filename.

Existing versions (`cli version list`):

- `v2.0.0` - frozen, what v0/v1 were actually trained on (docs/TRAINING.md)
- `v2.1.0` - frozen, prepared for v1.1 training (docs/TRAINING.md)
- `v3.0.0-seed` - this document's batch

None of these were overwritten by any other - each is independently
snapshotted and checksummed.

## Train / validation / test policy

`training/pipeline/split.py:stratified_three_way_split` - default 90/5/5,
stratified by intent (every class with ≥6 examples gets ≥2 val and ≥2
test examples; smaller classes go entirely to train, since they can't be
split meaningfully). **Test is held out and must never be used to tune
anything** - nothing in this pipeline reads `test.jsonl` except final
evaluation reporting; keeping it in its own file that no tuning code opens
by default is the structural safeguard. v3.0.0-seed: train=259, val=35,
test=35 (of 329 passing; the 4 "review" examples are excluded from all
three splits until resolved).

## Scaling strategy (this pipeline vs. millions of examples)

Every stage here was chosen to be cheap at this dataset's size while
staying honest about where it would need to change at real 1M+ scale:

| Stage | Current approach | What changes at 1M+ scale |
|---|---|---|
| Exact dedup | Hash set, O(n) | Unchanged - already scales |
| Near-dup | Shingle Jaccard, bucketed | MinHash/LSH (still no embeddings needed) |
| Semantic diversity | Shingle similarity + TTR proxy | Embedding-based clustering for genuine semantic (not lexical) similarity |
| Storage | JSONL | Parquet (columnar, compressed) once single-file JSONL becomes unwieldy - the schema (`RawExample`) doesn't change, only the on-disk format |
| Split | In-memory stratified split | Same algorithm, streamed rather than loading everything into memory at once |
| Language ID | Rule-based heuristic | Same approach remains viable (it's already O(n)); a real fastText/langdetect model would only be worth the dependency once volume clearly justifies it |

Nothing here was over-engineered for 333 examples, and nothing here
assumed the dataset would stay small.

Researched, not ingested - every candidate needs either (a) commercial-use

restriction, before any ingestion work starts:

| Dataset | Size/scope | License | Relevance / concern |
|---|---|---|---|

Hindi, 60 intents | **CC BY 4.0** (permissive, commercial OK w/ attribution) | Most promising by volume/license, but intents are generic voice-assistant (alarms, weather, music) - not WOW's call-handling taxonomy. | [AI4Bharat indicnlp_catalog](https://github.com/AI4Bharat/indicnlp_catalog) (CMU Romanized Hinglish Corpus, Hindi Twitter ~17.6M tweets) | Large, varied | Varies per sub-resource - needs individual verification | General Hindi/Hinglish text, not intent-labeled or call-domain; useful at most for phrasing/register reference, not direct ingestion. |
| PHINC (Hinglish social-media corpus) | ~13.7k sentences | Not clearly stated in available sources | Needs direct license verification before any use. |
| IIIT-H English-Hindi code-mixed corpus | ~6k sentences | Not clearly stated | Token-level code-mixing annotations - useful for language-ID calibration, not labeled intents. |
| HinGE (Hinglish generation dataset) | Research-scale | Not clearly stated | Same caveat as above. |
| hinglishNorm | Text normalization corpus | **CC BY-NC-SA** | **Excluded** - non-commercial clause incompatible with a product. |
| CALCS 2021 Eng-Hinglish | ~10k parallel pairs | Not clearly stated | Needs verification. |

**Nothing was ingested.** The one genuinely actionable path is MASSIVE
(permissive license, real volume, real Hindi) with a relabeling project -
a real but substantial undertaking, not a shortcut, and a decision for you
to greenlight given the relabeling cost.

## How to add new examples

1. Add hand-authored examples to `training/pipeline/generation/build_v3_seed.py`
   (or a new `build_v3_1_seed.py` for a distinct future batch), following
   the existing `_add`/`_add_many` pattern - the source string
   (`SOURCE = "hand_authored_v3"`) tracks provenance.
2. Regenerate: `backend\.venv\Scripts\python.exe -m training.pipeline.generation.build_v3_seed`
3. Validate and inspect before trusting it - see commands below.

## How to validate a new dataset

```powershell
backend\.venv\Scripts\python.exe -m training.pipeline.cli validate training/datasets/v3_raw/seed.jsonl
backend\.venv\Scripts\python.exe -m training.pipeline.cli dedupe training/datasets/v3_raw/seed.jsonl
backend\.venv\Scripts\python.exe -m training.pipeline.cli stats training/datasets/v3_raw/seed.jsonl
```

Inspect a specific example (by position or content hash):

```powershell
backend\.venv\Scripts\python.exe -m training.pipeline.cli inspect training/datasets/v3_raw/seed.jsonl --index 0
backend\.venv\Scripts\python.exe -m training.pipeline.cli inspect training/datasets/v3_raw/seed.jsonl --id <example_id>
```

Filter to just one quality status (e.g. to review what got flagged):

```powershell
backend\.venv\Scripts\python.exe -m training.pipeline.cli filter training/datasets/v3_raw/seed.jsonl --status review --output review_queue.jsonl
```

## How to create a training-ready dataset (score, split, version)

```powershell
backend\.venv\Scripts\python.exe -m training.pipeline.cli split training/datasets/v3_raw/seed.jsonl --version v3.1.0
backend\.venv\Scripts\python.exe -m training.pipeline.cli version verify v3.1.0
```

This scores every example, keeps only `status=pass`, stratified-splits
90/5/5, and writes `training/datasets/versions/v3.1.0/` with a checksummed
manifest. It does **not** train anything - the output is
`processed/{train,val,test}.jsonl`, ready to be pointed at from a
`training/configs/model_config_*.yaml`'s `dataset_dir` exactly like
v1.1's config does today (see `docs/TRAINING.md`).

## Remaining gaps (honest, not glossed over)

- **329 passing examples across 17 intents (~19/intent average) is below
  the 30+/intent floor** the v1.1 track already established - this batch
  validates the pipeline and the Hindi-dominant direction, it is not yet
  a standalone replacement for v1.1's dataset.
- **Context coverage is thin** (7-21 examples per mode) - the same
  weakness v1.1 targeted for the other track applies here too.
- **Hinglish (24.3%) and English (15.6%) both miss their targets** (30%/10%)
  - documented above, not silently corrected.
- **No external data has been ingested** - MASSIVE is the one clearly
  actionable opportunity found, gated on a relabeling decision.
- **4 examples remain in "review" status** (language-heuristic boundary
  cases) - excluded from the current split, awaiting a human call.
- **Near-duplicate/diversity checks are lexical (shingle-based), not
  semantic (embedding-based)** - a paraphrase using entirely different
  words wouldn't be caught as similar. Acceptable at this scale, flagged
  as the first thing to upgrade if volume grows substantially (see
  "Scaling strategy").
